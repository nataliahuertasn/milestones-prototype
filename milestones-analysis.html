C

Current Milestones logic — including the progress formula

The grid today

Four KPI tiles (SCOPES 18, MILESTONES 34, COMPLETED 18, PERCENTAGE 82.3%) over a table of QUOTE · SCOPE · PRICE · then one column per Phase. One row per scope, pulled automatically from every quote on the project — which is exactly the behaviour you want removed. Cells show a date, coloured green when met and red when not, with a pencil to edit and an eye to view; empty cells show a +.

The tile arithmetic does not close on its own numbers — 18 completed of 34 milestones is 53%, not the 82.3% displayed — so PERCENTAGE is already something more than a count. Almost certainly it is the weighted figure below, computed with weights that are today implicit.

The progress formula, recovered

Verified The July mockup prints the weights in the column headers (KICK OFF 5%, SD 5%, CP 5%, MATERIAL PROCUREMENT 15%, FABRICATION DRAWINGS 15%, PRODUCTION 30%, INSTALLATION DRAWINGS 15%, SHIPPING 10% — summing to 100) beside a PROGRESS column. I reproduced that column exactly:

progress(scope) = Σphases ( milestone.percentage × phase.weight ) ÷ Σphases phase.weight
✓ ROW B100·5 + 80·5 + 20·5 + 70·15 + 40·15 + 70·30 + 15·15 + 20·10 = 5175 ÷ 100 = 51.75 → mockup prints 52%
✓ ROW C100·5 + 15·5 + 25·5 + 70·15 + 15·15 + 50·30 + 35·15 + 15·10 = 4150 ÷ 100 = 41.5 → mockup prints 41%

This is the single most valuable thing to come out of the reference material. It means Weight is not a new calculation — it is the exposure of a constant that is already baked into the code somewhere. A developer's first job is to find where those 5 / 5 / 5 / 15 / 15 / 30 / 15 / 10 figures currently live: a hard-coded array, a per-phase column that Settings simply does not render, or a formula that assumes equal weighting. Which one it is changes the migration entirely, and I cannot tell from outside.

How a Group consolidates its Scopes

Verified The July mockup also shows a group row above its children, and its per-phase figures are a price-weighted average, not a plain one:

group.phase% = Σ ( scope.milestone.percentage × scope.price ) ÷ Σ scope.price
✓ SD(100·10 647 385 + 80·90 917 123 + 15·13 245 354 + 35·7 360 333) ÷ 122 170 195 = 71.98 → mockup prints 72% — a plain average would give 57.5%
✓ CP(100·10 647 385 + 20·90 917 123 + 25·13 245 354 + 20·7 360 333) ÷ 122 170 195 = 27.51 → mockup prints 28%

The group's own PROGRESS then comes from applying the phase-weight formula to that consolidated row (66.35 → 67% in the mockup ✓). So the two formulas compose cleanly: price-weight across scopes, phase-weight across phases.

One caveat I have to raise. A second mockup block includes a cancelled scope with a negative price (-13 245 354 COP) and no percentages, and there the printed group figures reconcile with no formula I can construct. Negative-price lines break price-weighting — they can drag a consolidated percentage above 100 or below zero. This is a real defect waiting to happen, not a mockup typo; see decision 4.

E

Proposed architecture

New persistence — two tables, nothing else

milestone_group ├─ id ├─ project_id FK → project (groups are scoped to a project, not a quote) ├─ name string, required — free text ├─ product_type_id FK → the Type of Scope catalogue, NULLABLE (see migration) ├─ index int — display order, same pattern as phase.index └─ created_at / updated_at milestone_group_scope join ├─ group_id FK, cascade delete ├─ scope_id FK, NO cascade from quote — see risk H-3 ├─ index int └─ UNIQUE (scope_id) ← enforces one-group-per-scope. See decision 2.

The existing Milestone table is not touched. Progress stays where it is — on the (scope × phase) cell. Groups are a presentation and roll-up layer laid over data that already exists. That is what protects existing projects, and it is why I recommend against storing progress on the group itself (decision 3).

Phase weight

phase └─ + weight decimal(5,2), NOT NULL, default 0 — percentage points, e.g. 30.00

Backfilled at migration with whatever constants the code uses today (section C), so that the day the column ships, every existing project's percentage is unchanged. If no such constants exist and progress is currently unweighted, backfill 100 ÷ count(phases) — also a no-op.

Pending-scope count — derived, never stored

pending = scopes of all quotes on the project WHERE scope_id NOT IN (SELECT scope_id FROM milestone_group_scope JOIN milestone_group USING(group_id) WHERE project_id = :project)

One LEFT JOIN … IS NULL. Every one of your eight triggers in §25 — new quote, new scope, group created, scopes added, scopes removed, group deleted — is satisfied for free, because the number is never cached. Storing it would create a second source of truth that has to be invalidated from the quote module, which is precisely the coupling to avoid. It ships on the same payload as the grid.

Decisions I need from you

Decision 1What does a grid cell show — the date or the percentage?

Today's grid shows dates with red/green status. The July mockup shows percentages. The underlying record has both. Showing percentages is what makes the weighted roll-up legible; showing dates is what your team is trained on and what carries the schedule signal.

RecommendationPercentage as the cell value, with the date's red/green colour retained as the cell's status treatment, and the date on hover. You lose nothing and the group row becomes meaningful. But this changes a screen people use daily — your call, not mine.
Decision 2Can one Scope belong to two Groups?

You asked me to validate this (§12). If it is allowed: the pending count still works, but the project percentage double-counts that scope's price, and "remove from group" becomes ambiguous.

RecommendationNo — enforce it with a UNIQUE constraint on scope_id. A group is an organisational bucket, and buckets that overlap make the consolidation arithmetic unsound. "Move to another group" covers the real need. This also makes the pending count a clean partition: every scope is in exactly one group, or pending.
Decision 3Group-level progress: stored, or written down to the scopes?

Your §13 Option A says progress can be recorded "directly on the Group". The July spec is more specific: entering progress on the group row applies it to every child scope — a bulk fill, not a separate value.

RecommendationThe July reading. Keep one source of truth — the (scope × phase) cell — and make the group row a bulk-edit control that writes to its children, then reads back as the price-weighted roll-up. Storing a group percentage alongside child percentages creates two numbers that disagree the moment anyone edits a child, and there is no non-arbitrary rule for which wins.
Decision 4Cancelled and negative-price scopes

Price-weighting is undefined when prices can be negative, and your data contains them (a cancelled line at -13 245 354 COP). A negative weight inverts that scope's contribution: 0% progress on a negative line raises the group average.

RecommendationExclude scopes with price ≤ 0 from the weighting denominator while still showing them in the group (greyed, no progress input). If cancelled lines are flagged in the data rather than merely negative, use that flag instead. Either way this needs to be a stated rule, because the mockup does not have one.
Decision 5Must Phase weights sum to exactly 100?

Because the formula divides by Σ weight, a total of 90 or 110 still produces a sensible number — it self-normalises. So a hard block is not needed for correctness, and a hard block makes editing miserable: you cannot get from one valid configuration to another without passing through an invalid one.

RecommendationHard-validate the field (numeric, 0–100, up to 2 decimals, empty → 0, negatives rejected inline). Soft-validate the total: a live running sum under the table, amber when ≠ 100, with the note that progress is normalised over the total. Save is never blocked. Weights are global, so changing one silently moves every project's percentage — the confirmation dialog should say so.

H

Risks

H-1 · Existing projects go blank on deploy highest

This is the one that will hurt. The moment the grid stops auto-loading scopes, every project that has milestone data shows an empty Milestones tab. No row is deleted — the Milestone records are untouched — but to a Project Manager it is indistinguishable from losing months of work, and it will be reported as data loss within the hour.

Mitigation: backfill one group per existing project. For every project having at least one Milestone record, create a group named after the project (or “All Scopes”), product_type_id = NULL, containing every scope that has at least one milestone. Those projects then open expanded and look almost identical to today, with their pending count showing whatever scopes were never touched. It is reversible, non-destructive, and it turns a migration into a no-op from the user's side.

This is why product_type_id must be nullable in the schema — we cannot invent a Type of Scope for migrated groups, and forcing one would mean guessing. The field is required in the create form, optional in the column, and migrated groups show it blank until a PM fills it in.

H-2 · The weight constants may not exist

Section C proves weights are applied today. It does not prove they are stored. If they are a hard-coded array, moving them to the database is a behaviour change for every project simultaneously — safe only if the backfill reproduces them exactly. If progress turns out to be computed some other way and my two arithmetic checks were coincidence, the whole of section C needs redoing against the code. Confirm before writing the migration.

H-3 · Deleting a quote

If a quote is deleted or a line removed, orphaned rows in milestone_group_scope would break the group roll-up. Whatever the quote module does today to Milestone records must be mirrored — which I cannot see. If quotes are soft-deleted, the pending count must exclude soft-deleted scopes or it will report phantom pending work forever.

H-4 · Weight is global, progress is per-project

One PM editing weights in Settings moves the reported percentage of every project in the company, including closed ones and anything already reported to a client. Worth a confirmation dialog naming the count of affected projects; worth asking whether weights should eventually be snapshotted per project. Out of scope now, but it should be a conscious deferral rather than an oversight.

H-5 · Naming

"Milestones" already means the Phase catalogue in Settings. Adding "Milestone Group" gives the word three meanings. Consider labelling the Settings tab Phases as part of this work — a one-word change while that screen is already open.
